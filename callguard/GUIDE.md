# GUIDE: rebuild and run Sherlock Phones (for a reviewer or their coding agent)

Sherlock Phones checks Swiss German bank phone calls for compliance problems. A call goes in as a `.wav`; out come
**Alarm / Prüfen / Kein Alarm**, the facts and rules behind the decision, and timed audio passages. Everything runs on
your own GPUs; no cloud API is called. Package and CLI are named `callguard`.

This file is complete on purpose: an agent that follows it top to bottom, with the hardware below, reproduces our
results (reader B, Kev-4B, uses the Kev code in `../fraud_analysis/kev`, set up in §3; `NO_KEV=1` runs Qwen alone). Measured numbers are in [`RESULTS.md`](RESULTS.md) (all generated by this code from the case `.wav` files).

## 1. What runs, in order (production profile `sherlock`, `config/sherlock.yaml`)

| # | step | model / method | where |
|---|---|---|---|
| 1 | transcription | Whisper large-v3, Swiss German fine-tune `gcoli/whisper-large-v3-swiss-german-mit` (faster-whisper, fp16): hears Swiss German, writes Standard German, word timestamps | GPU, ~4 GB |
| 2 | who speaks when | sherpa-onnx: pyannote segmentation-3.0 + WeSpeaker ResNet34, 2 voices, segments split at speaker changes | CPU |
| 3 | who is the advisor | Qwen3.8-27B 3-bit (`unsloth/Qwen3.8-27B-GGUF`, UD-IQ3_XXS) on llama.cpp `llama-server`; asked again with the speaker labels swapped, otherwise first speaker = advisor | GPU, ~11 GB |
| 4 | facts, reader A | Qwen3.8-27B answers every yes/no fact of the policy table (`config/policy_table.yaml`, 28 facts in 5 families) on the whole call: p(ja / nein / unklar) from the answer token's log-probabilities; for facts it says yes to, it names the segments + a German reason | GPU (same server) |
| 5 | facts, reader B + passages | Kev-4B (`jaredpalmer/kev-4b`) answers every fact again: p(ja). For facts with p(ja) > 0.5 it finds the passage by masking: remove one 4-segment window at a time, re-ask, the window whose removal drops p(ja) most is the passage (`src/callguard/checks/kev_facts.py`) | GPU, ~8-12 GB |
| 6 | combine readers | fact policy (`config/fact_policy.yaml`): per reader yes ≥ 0.6, no ≤ 0.4, else unclear; a fact is yes/no only when both readers agree, otherwise unclear | no model |
| 7 | rules | policy table rules per family (access, trade, disclosure, splitting, documentation), first matching rule wins, e.g. "code spoken = ja and still valid = ja → Alarm"; an unclear decisive fact → Prüfen | no model |
| 8 | light cues | keyword list (`config/keywords.json`, fuzzy) + regex patterns (codes, IBAN, amounts); small weights, they cannot decide alone | no model |
| 9 | decision | weighted fusion per family (facts 1.0, keywords 0.15, patterns 0.1), threshold 0.55 with a review band; disagreement / uncertainty escalates to Prüfen | no model |
| 10 | display only | Swiss German transcript per segment from a wav2vec2 SwissDial dialect model (ONNX); runs after the decision, never read by a check | CPU |

The models run one after another (`scripts/run_testset.sh` starts and stops each server), so one 12 GB GPU is enough.
With two GPU hosts, split the calls by audio length and run each half on its own host (section 4).

## 2. Requirements

- Linux, NVIDIA GPU with **≥ 12 GB** VRAM (tested: RTX 4070 SUPER 12 GB, RTX A5000 24 GB), driver ≥ 535.
- CUDA toolkit 12.x (`nvcc`) to build llama.cpp, cmake, a C++ compiler, git, ffmpeg.
- Python 3.12 via [uv](https://docs.astral.sh/uv/). ~35 GB free disk, 16 GB RAM, internet for the first downloads.
- For the dashboard: Node.js ≥ 22.17 (npm; `frontends/swiss/.npmrc` enforces the engine version).

## 3. Install (once, ~45-60 min, mostly downloads)

```bash
git clone git@github.com:markandrewc/sprintd_zurich.git && cd sprintd_zurich/callguard   # all commands below run here

# Python environment (app + ASR + diarization)
uv sync --extra asr --extra diarize --extra ui --extra dev   # ui: the tests also cover the older Streamlit views
# cuBLAS / cuDNN for faster-whisper. REQUIRED on hosts without a system CUDA 12 runtime
# (without it step 1 fails with "libcublas.so.12 is not found"); run_testset.sh sources scripts/remote/cuda_env.sh
uv pip install --target .cuda-libs nvidia-cublas-cu12 "nvidia-cudnn-cu12==9.*"

# ASR + diarization models -> models/ (~3.5 GB), Swiss German display model (CPU)
scripts/download_models.sh gpu
scripts/gsw/setup_model.sh

# llama.cpp with CUDA. CMAKE_CUDA_ARCHITECTURES: 89 = RTX 40xx, 86 = RTX 30xx / A5000, or "native"
git clone --depth 1 https://github.com/ggml-org/llama.cpp ~/repos/llama.cpp
cmake -S ~/repos/llama.cpp -B ~/repos/llama.cpp/build -DGGML_CUDA=ON -DCMAKE_CUDA_ARCHITECTURES=native \
      -DLLAMA_CURL=OFF -DCMAKE_BUILD_TYPE=Release
cmake --build ~/repos/llama.cpp/build -j --target llama-server
# elsewhere? export LLAMA_SERVER=/path/to/llama-server

# Qwen3.8-27B, 3-bit GGUF (10.9 GB)
uvx --from huggingface_hub hf download unsloth/Qwen3.8-27B-GGUF Qwen3.8-27B-UD-IQ3_XXS.gguf \
    --local-dir models/llm/qwen38-27b-gguf

# Kev-4B runtime: the Kev service code is in this repo's parent folder (../fraud_analysis/kev); its Python env goes to
# ../.venv-kev, where run_testset.sh finds it. scripts/remote/serve_kev.py serves it on :8003.
# Without it only NO_KEV=1 runs (Qwen alone; see RESULTS.md for what that costs).
(cd .. && uv venv .venv-kev -p 3.12 \
  && uv pip install -p .venv-kev torch --index-url https://download.pytorch.org/whl/cu126 \
  && uv pip install -p .venv-kev "transformers>=5" accelerate "peft>=0.21" "pydantic>=2.9" fastapi uvicorn httpx huggingface_hub)
# first Kev start downloads jaredpalmer/kev-4b + Qwen/Qwen3.5-4B-Base (~8 GB) into ~/.cache/huggingface

# offline tests (no GPU, no case data needed; ~5 min)
uv run pytest -q -m "not slow"   # tests that need the case data or downloaded models skip without them
```

## 4. Run calls (the hidden test set or any folder of `.wav`)

One host:
```bash
scripts/run_testset.sh /path/to/wavs sunday          # -> runs/testset-sunday/  (timings.tsv = seconds per stage)
```
Two hosts (what we measured in `RESULTS.md`): split by audio length, run each half, then copy one run folder next to the
other (call ids are the file names, so the halves never collide):
```bash
python3 scripts/split_wavs.py /path/to/wavs /tmp/half1 /tmp/half2            # equal audio length
# hosts of different speed: --speeds 23 35 (seconds per audio minute of each host, from a run's timings.tsv)
# host 1: scripts/run_testset.sh /tmp/half1 sunday-a        host 2: scripts/run_testset.sh /tmp/half2 sunday-b
# then on the dashboard host:
mkdir -p runs/testset-sunday/sherlock runs/testset-sunday/qwen/sherlock-qwen
cp -r <host1>/runs/testset-sunday-a/sherlock/* <host2>/runs/testset-sunday-b/sherlock/* runs/testset-sunday/sherlock/
cp -r <host1>/runs/testset-sunday-a/qwen/sherlock-qwen/* <host2>/runs/testset-sunday-b/qwen/sherlock-qwen/* runs/testset-sunday/qwen/sherlock-qwen/
```
What the script does: (1) Whisper transcribes every call; (2) llama-server with Qwen3.8 up: roles, reader A, evidence
(Qwen-only decision kept as a fallback in `qwen/sherlock-qwen/`); (3) Qwen down, Kev up: reader B + Kev passages, final
two-reader decision in `sherlock/<call>/result.json`; (4) Swiss German display view on the CPU.
Options: `NO_KEV=1` (Qwen only), `NO_GSW=1`, `CACHE_DIR=/tmp/fresh` (separate cache, e.g. for timing),
`LLAMA_SERVER=...`, `Q38_GGUF=...`, `KEV_REPO=...`, `OUTCEPT_URL=http://<host>:8080/triggers`.

**No hints from file names or case data:** the pipeline only reads the audio; the file stem is just the call id.
`run_testset.sh` points `paths.data_dir` at an empty folder for every pipeline stage, so no code path can look up a case label,
script or "Sollbewertung" by file name. To be sure, rename the files first (we ran our measurement on `c01.wav ...`).

## 5. Dashboard

**Without a GPU** (only Python + Node): the stored results of our runs are in the repo, so the dashboard works right
after `uv sync` and `npm ci` (no audio in the repo: the player then follows the transcript on a timer):
```bash
uv run callguard api -c sherlock --set paths.runs_dir=results/overnight-60 --set paths.data_dir=results/overnight-60/.no_case_data --port 8600
uv run python scripts/score_results.py results/overnight-60/sherlock results/overnight-60/labels.csv   # the numbers in RESULTS.md
```

**On a new run:**

```bash
uv run callguard api -c sherlock --set paths.runs_dir=runs/testset-sunday --set paths.data_dir=runs/testset-sunday/.no_case_data --port 8600
cd frontends/swiss && npm ci && npm run dev -- --port 8605          # http://localhost:8605
```
Start the API from the repo root (audio paths in the results are relative to it). The dashboard shows only the calls of
that run folder: list with the three counts, call page with player, synced transcript (Standard German / Swiss German),
passages with reason, the facts of both readers, rules, keywords, threshold. Settings edits rewrite
`config/policy_table.yaml` / `config/keywords.json`: back them up before a demo.

## 6. Score (only if labels are given)

```bash
# labels.csv: call_id,expected   (expected = alarm | review | no_alert; call_id = wav name without .wav)
uv run python scripts/score_results.py runs/testset-sunday/sherlock labels.csv
```
Scoring reads the labels only after the run, from your csv; nothing in the pipeline sees them.

## 7. Troubleshooting

- `libcublas.so.12 is not found` → the `.cuda-libs` step in section 3.
- llama-server or Kev out of memory → another process holds the GPU (`nvidia-smi`); stop it by PID. The script's own
  servers: `runs/logs/llamacpp.pid`, `runs/logs/kev.pid`. Never `pkill -f` (it matches its own shell).
- Port 8003 / 8004 already in use → an old Kev / llama-server (or an ssh tunnel) is still running; the script would
  silently talk to it. Stop it first.
- `PinnedLLMError` in `run_kev.log` → a Qwen answer missing from the cache (stage 2 failed for that call); rerun.
- Dashboard says "API nicht erreichbar" → start the API (section 5) from the repo root.

## 8. Repository map
